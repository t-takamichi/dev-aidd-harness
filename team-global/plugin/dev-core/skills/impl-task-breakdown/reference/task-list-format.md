# タスク一覧フォーマット

配置: `{対象MS}/docs/{プロジェクト}/README.md`

## 命名

| 項目 | 規則 | 例 |
|------|------|----|
| ID | `T` + 連番2桁（100件超は3桁）。**一度振ったら変えない**。欠番可。並び順とは無関係 | `T01` |
| タスク名 | 人が読む名称（日本語可） | 注文登録APIの追加 |
| slug | 英小文字・数字・ハイフン | `add-order-api` |
| ディレクトリ名 | `{ID}-{slug}` | `T01-add-order-api` |

- 追加は新しい ID を振る。分割は元 ID を残し、新規分を新 ID にする。削除は行を残して状態を `廃止` にする。
- ID・ディレクトリ・詳細リンクの一致は `scripts/validate-tasks.py` で検証する。

## テンプレート

```markdown
# {プロジェクト} タスク一覧

- 対象MS: {対象MS（リポジトリ相対パス。絶対パスは書かない）}
- 元設計書: {設計書のパス（リポジトリ相対）}
- 要件・決定: [requirements.md](requirements.md) / [decisions.md](decisions.md)
- 作成日: YYYY-MM-DD
- ステータス: draft | reviewed | approved（draft 中の README は draft / reviewed。approved は本番反映時に付ける）

## 概要

{このプロジェクトで何を実現するかを2〜3行}

## タスク

| ID | タスク名 | 概要（何をすべきか） | 種別 | 依存 | 規模 | 根拠（設計書 / 決定ログ） | 詳細 | 状態 |
|----|----------|----------------------|------|------|------|----------------|------|------|
| T01 | 注文登録APIの追加 | 注文登録 API を追加する | API | - | M | 3.2節 | [task.md](T01-add-order-api/task.md) | active |

## 依存関係

{依存が複雑な場合のみ。mermaid の graph で記載}

## 未確定事項

| # | 内容 | 影響するタスク | 確認先 |
|---|------|----------------|--------|

## 提案（設計書に無いが必要と思われるもの）

{なければ「なし」}
```

## 列の定義

| 列 | 内容 |
|----|------|
| 概要 | 1〜2文。「何を」「どこに」するかが分かること。実装方法は書かない |
| 種別 | `API` / `DB` / `画面` / `バッチ` / `共通` / `設定` / `結合テスト` / `その他` |
| 依存 | 先行タスク ID（カンマ区切り）。なければ `-` |
| 規模 | 参考値。変更対象数（ファイル・テーブル・IF の合計）で判定。`S`: 1〜2 / `M`: 3〜6 / `L`: 7〜10。11以上は分割する |
| 根拠 | 元になる設計書の章・節（複数可）。決定ログ由来なら `Q3` のように書く |
| 詳細 | タスク詳細へのリンク（一覧からの相対パス） |
| 状態 | `active` / `廃止` |

## 並び順

表の行順だけで表す。**依存先が必ず上の行に来る順**（トポロジカル順。`validate-tasks.py` が検査する）。同順位は種別 `DB` → `共通` → `API` → `画面` → `バッチ` → `結合テスト`。

## テストの扱い

各タスクの単体テストはそのタスクに含める。`結合テスト` 種別は、複数タスクに跨る結合・E2E に限る。結合テスト・横断要件（認証など）のタスクは、他タスクの要件を「参照」として持つ（タスク詳細の要件表の区分）。
