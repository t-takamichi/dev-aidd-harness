# タスク詳細フォーマット

配置: `{対象MS}/docs/{プロジェクト}/{ID}-{slug}/task.md`

タスク詳細はプログラミング詳細設計の INPUT になる。「何を満たすべきか」「どこを触るか」を書き、「どう書くか」（クラス構成・擬似コード）は書かない。

**種別・規模・依存・概要・状態は書かない**（一覧が正。二重管理を避ける）。

## テンプレート

```markdown
# {ID} {タスク名}

- 一覧: [README.md](../README.md)

## 目的

{なぜこのタスクが必要か。1〜3行}

## 実装スコープ

### やること

- {変更・追加する内容を箇条書き}

### やらないこと

- {隣接タスクとの境界。別タスクで扱うものはその ID を書く}

## 要件

| 要件ID | 区分 | 要件 | 根拠 |
|--------|------|------|------|
| R-001 | 主担当 | {満たすべき振る舞い・仕様} | {設計書の章・節 or 決定ログ Q#} |

- 要件ID は `requirements.md` のインベントリの ID を使う。
- 区分: `主担当`（実装責任を持つ。1要件につき1タスクだけ）/ `参照`（結合テスト・横断要件などで関わるだけ）。

## 対象箇所

| 区分 | パス / 名称 | 変更内容 |
|------|-------------|----------|
| 変更 | {既存ファイル・クラス・テーブル} | {概要} |
| 新規 | {追加予定の場所・名称} | {概要} |

## インターフェース

{API・イベント・DB スキーマなど、外部から見える入出力。設計書から転記・要約し、出典を書く。なければ「なし」}

## 受け入れ条件

- [ ] {完了と判定できる、検証可能な条件。要件ID と対応させる}（R-001）

## テスト観点

- {正常系・異常系・境界の観点を箇条書き。テストコードは書かない}

## 未確定事項

| # | 内容 | 想定 | 確認先 |
|---|------|------|--------|

## プログラミング詳細設計への引き継ぎ

{詳細設計で決めるべきこと、注意点、参照すべき既存実装}
```

## 書き方

- 全要件に根拠（設計書の章・節 or 決定ログ Q#）を付ける。決定ログは `decisions.md`。根拠がないものは「提案」または「未確定事項」に回す。
- 受け入れ条件は全要件に最低1つ対応させる。
- 「やらないこと」は必ず埋める（スコープ漏れ・重複を防ぐ）。
