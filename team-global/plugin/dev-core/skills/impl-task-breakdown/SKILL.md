# impl-task-breakdown

設計書から実装タスク一覧とタスク詳細を作成する。タスク詳細は、後続のプログラミング詳細設計の INPUT になる。

## 出力先

`{プロジェクトDir}` = `{対象MS}/docs/{プロジェクト}`

| 対象 | パス |
|------|------|
| タスク一覧 | `{プロジェクトDir}/README.md` |
| タスク詳細 | `{プロジェクトDir}/{ID}-{slug}/task.md` |
| 要件インベントリ | `{プロジェクトDir}/requirements.md` |
| 決定ログ | `{プロジェクトDir}/decisions.md` |
| 作業ファイル | `{プロジェクトDir}/_work/`（調査結果・ドラフト・レビュー。構成は `reference/workflow.md`） |

- フォーマットは `reference/task-list-format.md` と `reference/task-detail-format.md`。
- 要件インベントリと決定ログは、タスクの根拠として残すため本番パスに置く（`_work/` はコミット不要）。
- ドラフトは `_work/draft/` に作る。本番へ反映するのは手順7の承認後に1回だけ。
- 読むリファレンス、スクリプト、エージェントに渡すパスは、すべて絶対パスに解決してから使う。
- 小規模（タスク5件程度）は `reference/workflow.md` の「小規模ルート」で簡略化してよい。

## 手順

1. **INPUT 受領**: 設計書（パスまたは本文）、`{対象MS}`（絶対パス）、`{プロジェクト}` を受け取る。
   - 本文で受け取った場合は `_work/design-input.md` に保存する（サブエージェントは会話を読めない）。
   - 対応形式は Markdown / テキスト / PDF。それ以外（xlsx・docx・外部Wiki等）は Markdown に変換して保存する。
   - `{プロジェクトDir}/README.md` が既にあれば**更新モード**（`reference/workflow.md`）で進める。
   - `decisions.md` は空でもよいので必ず作る。
2. **調査**: `design-investigator` を観点・章単位で並列起動する（依頼テンプレートは `reference/workflow.md`）。結果は `_work/investigation-*.md` に書かせ、メインには要約だけ返させる。
   - 要件インベントリ（`requirements.md`、R-001… 出典付き）は、調査結果の要件候補をメインが統合して作る。設計書の全文をメインが直接読まない。
   - メインは観点間の矛盾を突き合わせ、解消できないものを手順3の質問に回す。
3. **質問**: 不明点・矛盾・前提不足を AskUserQuestion で聞く。
   - 調査やコードで解決できるものは聞かない。
   - 1回の呼び出しは4問まで。優先度順に複数回に分ける。選択肢にできない質問は通常のテキストで聞く。
   - 再質問は2ラウンドまで。残りは「未確定事項」に回す。
   - **回答は必ず `decisions.md` に Q 番号付きで保存する。** 回答から新しい要件が生まれたら `requirements.md` に出典 `Q#` で R-ID を追加する。
4. **ドラフト作成**: `_work/draft/` に作る。根拠は設計書の章・節か決定ログ Q# のみ。未解決は推測で埋めず「未確定事項」に残す。タスクが多い場合はタスク群ごとに詳細を作る。
5. **機械チェック**: `python3 {スキルDir}/scripts/validate-tasks.py {プロジェクトDir}/_work/draft` を実行し、NG を直す。`{スキルDir}` はこのスキルの絶対パス。
6. **レビュー**: `task-draft-reviewer` を起動する（依頼テンプレートは `reference/workflow.md`）。結果は `_work/review-{n}-{群}.md` に保存する。
   - レビューは最大3回。2回目以降は前回指摘の解消確認と、新規 blocker のみを見る。
   - blocker / major が 0 件になったら README のステータスを `reviewed` にして手順7へ。ある間は手順4へ戻る。
   - 3回で収束しなければ、残課題を添えてユーザーに判断を仰ぐ。
   - タスクが10件を超える場合は、詳細レビューをタスク群・章範囲ごとに並列に分け、全体レビューは一覧とカバレッジに絞る。
7. **ユーザーレビュー**: 反映先のパス、タスク数、未確定事項、レビューでの主な修正点を伝えて確認を依頼する。
   - 差し戻された場合は手順4に戻る。修正後のレビューは、修正箇所と新規 blocker のみを対象に行う。blocker / major が出れば手順4へ（回数は数え直す）。
   - 承認されたら `_work/draft/` を本番パスへ反映する（既存ファイルがある場合はこのとき差分を示す）。README のステータスを `approved` にする。

## 守ること

- 設計書にない要件を足さない。必要と思うものは「提案」に分けて書く。
- タスク詳細に実装コード・クラス詳細は書かない（プログラミング詳細設計の役割）。
- 一覧のタスク属性（種別・規模・依存・概要）は一覧だけに持つ。詳細に複製しない。
- 一度振った ID と R-ID・Q 番号は変えない。

## リファレンス

- `reference/task-list-format.md` — タスク一覧のフォーマット
- `reference/task-detail-format.md` — タスク詳細のフォーマット
- `reference/workflow.md` — 作業ファイル、エージェントへの依頼テンプレート、更新モード、小規模ルート
